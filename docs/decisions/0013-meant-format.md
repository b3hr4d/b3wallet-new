# 0013: Values shared with the profile spec come from @meantjs/format

Status: proposed, 2026-10-28.

**Decision: the MCP server and the UI take the rules they share with the
Candid Profile spec from Meant's `@meantjs/format`, pinned to the exact
0.1.0: the names rule an account's label is resolved by, amounts read and
shown exactly, and memos read and shown as text or as 0x and hex. A profile
of `wallet.did`, with the agent's tools and the owners' consent text
generated from it, waits until the spec can say what this interface needs
(below).**

The wallet writes the meaning of its values by hand, twice: the UI for the
owners (`ui/src/logic/describe.ts`) and the MCP server for the agent
(`mcp/src/tools.ts`). The two copies had drifted. An agent writes a memo as
text ("rent"), but the Approvals page showed it to the owner as hex
(`72656e74`), and the MCP server had copied the spec's names rule into its
own code. Meant (B3Pay/Meant) published the profile libraries to npm on
2026-10-28 with signed provenance. `@meantjs/format` is one of them: exact
value text for the spec's value tags and the names rule, with no dependency
and no Node built-in, and checked against the vectors every implementation
of the spec shares.

| Option | What it is | For | Against |
| --- | --- | --- | --- |
| **A. `@meantjs/format` where the rule is the spec's** | The names rule, amounts and memos in `mcp/`, and memos in `ui/` | One rule for the wallet, its agent and every other profile consumer. The owner reads the agent's memo as text. A ledger whose symbol hides a right-to-left override or another invisible character is one the agent neither shows nor sends. 2,974 more bytes of `app.js` | One more package in the signed release (listed in `ui/build.mjs`) |
| B. A profile of `wallet.did`, with tools and consent generated by `@meantjs/profile`, `/tools` and `/consent` | The interface's meaning written once, as data, and the MCP tools and an ICRC-21 consent message made from it | The agent's tools and the owner's text come from one document, and the wallet's declared ICRC-21 gets an implementation | The spec cannot say it yet: `propose(Action)` holds transfers, policy changes and upgrades in one argument, but an effect is only for a whole method. `to` is text, an ICRC-1 account or a Bitcoin or EVM address depending on the chain. A transfer's decimals come from the ledger of the `from` account. A transfer's outcome arrives later, in the audit log, not in the reply. And `wallet.did` imports `common.did`. It would also move the UI to `@candid-core/schema` 0.5.0 and the cli to 0.4.0 |
| C. Keep writing it by hand | As before | No new dependency | Two copies that drift, as the memo did |

What changes with A:

- `mcp/`: `accountNamed` resolves a label with `resolveName`. It is the same
  rule (NFKC, lowercase, whitespace runs made one space; an address is never
  a name; exactly one match, or the agent asks), and the server's tests pass
  unchanged. `amount` is read by `parseAmount`. It takes the token's symbol
  or none ("1.5", "1.5 ICP"), refuses a different symbol, "1,5", "1e3" and
  more decimal places than the token has, and never rounds. Amounts are shown
  by `displayAmount`. `memo` is read by `parseBytes` as UTF-8, or as hex
  after 0x, within 32 bytes. It is shown as the quoted text when it is text
  without control or invisible characters, and as 0x and hex otherwise.
- `ui/`: the Approvals page and the rail show a transfer's memo by the same
  rule (`Memo: “rent”.`, `Memo: 0x0a0b.`). Only `bytes.mjs`, `util.mjs` and
  `errors.mjs` of the package are bundled. `app.js` grows from 540,921 to
  543,895 bytes, and the pages' HTML does not change.
- Left as it is: the UI's send page reads amounts with ic-reactor's
  `parseUnits`, which also refuses excess precision, and the UI and the
  server keep their own names for chains and account kinds. These are the
  wallet's own words, not the spec's.

What B waits on: the spec items for a variant case's effect and intent, an
address given as text, a value that depends on another argument of the call,
an outcome that arrives through another method, and `.did` files that
import others. All five are proposed in Meant and not decided yet. A draft
profile of `wallet.did` as of commit c88908e (2026-10-22) resolves with no
error, and set beside this repository's hand-written texts it is where these
gaps were found. Once they are decided, it would need refreshing for today's
interface before B could start.
